# familiar-ai 設計方針：MI 間の関係（v0.10・全 5 段 実装済み）

## この文書の位置づけ

記録どうしの関係を、二項の列から**多項の関係**へ移す設計を定める。多項の関係とは、二つの
記録を結ぶ辺ではなく、何個の記録でも項として持てる一つのまとまりのことである。

`設計方針_求めの版チェーン` は `superseded_by` から解決の意味を外し、版履歴に絞った。この
文書はその先を扱う。版履歴そのものを含めて、記録どうしの関係の表現を一つの器へ集める。

課題8 の記-e（応答した発話を閉じる）は、この設計に吸収される。閉じるという操作そのものを
置かないので、記-e が想定していた作業は残らない。

## 原因

### `superseded_by` が改訂以外の意味を持ち続けている

`superseded_by` を書く箇所は 6 つある。

| 箇所 | 何を書くか | 意味 |
|---|---|---|
| `agent.py:493` | 自分が答えた逐語を会話要約で畳む | 要約への畳み込み |
| `event_loop.py:300` | 鎖の前進 | 前後関係 |
| `event_loop.py:327` | 版チェーンを進める | 改訂 |
| `event_loop.py:1051` | 配れた保留発話を新しい起点で畳む | 解決 |
| `io/oif.py:261` | 口の通し | 呼び手による |
| `migration/019`、`052` | 一回きりの整理 | 重複の畳み込み |

改訂と呼べるのは `event_loop.py:327` だけである。残りは、畳まれた側が誤りになったわけでは
ない。要約に吸われた逐語も、配り終えた保留発話も、その時点の事実としては正しい。

### 記録どうしの関係を表す手段が三つしかない

`observations` が持つ関係は、後ろ向きの `parent_id`（この記録を起こしたもの）、前向きの
`superseded_by`（置き換えたもの）、絶対時刻の `timestamp` である。同じやりとりの続きである
ことを表す関係は無い。

順序を持つ関係が必要になったとき、使えるのは `superseded_by` だけだった。だから前後関係を
表したい箇所が改訂の列へ寄り、意味が混ざった。

### 二項では、やりとりが一つの関係にならない

一つのやりとりは、問い、調べた版、答えの逐語、会話要約という複数の記録からなる。二項の辺を
並べても、そのまとまりを一つの関係として指せない。

### 畳むことが想起からの除外と同義になっている

想起の全経路が `superseded_by IS NULL` で絞るので、畳まれた記録は想起の母集合から消える。
自分が答えた逐語は 464 件のうち 453 件（97.6%）が会話要約へ畳まれており、残るのは軽量LLM の
一文（80 トークン上限）だけである。細部のベクトルが存在しないので、細部での近接は起きない。

### 時系列を短時間で追う経路が無い

主LLM へ渡るのは `messages=[user_msg]` の一通だけで、中身は現在の発話一つである
（`event_loop.py:1227`、`1230`）。会話履歴 `agent.messages` は追記する箇所が 0 件で、いつも
空である。時刻順に直近を読む `recency_fallback`（`store/observations.py:462`）は呼び手が
0 件で、`get_observations_for_date` を使うのは日次要約だけである。

W は適合度の降順に並ぶ（`event_loop.py:773`）ので、時系列の連なりにはならない。

## 対応

### 器の形

関係そのものを表すヘッダと、その項を表す行に分ける。`wr_records` と `wr_record_items`
（`migration/030`）が既に取っている形である。

```sql
CREATE TABLE relations (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    kind       text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE relation_members (
    relation_id bigint NOT NULL REFERENCES relations(id) ON DELETE CASCADE,
    obs_id      text   NOT NULL,
    role        text   NOT NULL,
    position    int,
    PRIMARY KEY (relation_id, obs_id, role)
);

CREATE INDEX idx_relation_members_obs ON relation_members(obs_id, role);
CREATE INDEX idx_relations_kind        ON relations(kind);
```

主キーを `(relation_id, obs_id, role)` にするのは、同じ観測が同じ関係の同じ役割で二度入る
形が、改訂にも継起にもやりとりにも共起にも無いためである。項を数え上げる側の取り違えが、
黙って通らずにここで落ちる。

索引は二つ置く。`idx_relation_members_obs` は観測から関係を引く道で、段 2 の想起の絞りが
ここを通る。`idx_relations_kind` は種類で絞る道である。

三つの語を定める。

- **種類**（`kind`）：その関係が何を表すか。改訂、継起、やりとり、共起、解決
- **役割**（`role`）：その項が関係の中で何であるか。旧と新、前と後、問いと答え
- **位置**（`position`）：項の順序。順序を持たない関係では `NULL`

項の識別子は観測の id にする。`wr_record_items.mi_id` は名前に反して観測の id を持っており
（`diffuse_store.py:109` が `o.id::text = i.mi_id` で結合する）、`superseded_by` と同じ粒度
である。粒度を揃えたまま移せる。

### 何がこの器に載るか

| 種類 | 項と役割 | 位置 | いまの表現 |
|---|---|---|---|
| 改訂 | 旧、新 | あり（2 項） | `event_loop.py:327`（版チェーン） |
| 畳み込み | 旧、新 | あり（2 項） | `agent.py:493`（答えの逐語を会話要約へ） |
| 解決 | 旧、新 | あり（2 項） | `event_loop.py:1051`（配れた保留発話） |
| 前進 | 旧、新 | あり（2 項） | `event_loop.py:300`（鎖の前進） |
| 継起 | 前、後 | あり | `_begin_origin`（ターンどうしの起点をつなぐ） |
| やりとり | 起点、版、見た、答え、要約 | あり（多項） | `_note_record` と `record_exchange` |
| 共起 | 項（W の全要素） | 無し（多項） | `record_cooccurrence`（060 で `wr_records` から移した） |

やりとりが多項であることが、二項の列では表せなかったものにあたる。問いと答えを別々の辺で
つなぐのではなく、一つの関係の項として順序つきで並べる。

会話は関係の連なりをたどる経路になる。何歩さかのぼるかで窓の大きさが決まるので、数秒の
追跡と数か月の想起が同じ仕組みで出る。単一の識別子で区切らないから、会話の境界を決める
必要も無い。

### 想起に出さない役割が二つある

上の四つ（改訂、畳み込み、解決、前進）は、理由は違うがどれも「この記録はもう現行では
ない」という同じ帰結を持つ。そこで**役割 `旧` にその帰結を担わせ、種類は理由だけを言う**
ことにする。想起の絞りは種類を見ずに済み、結合の要らない一文になる。

```sql
NOT EXISTS (SELECT 1 FROM relation_members m
            WHERE m.obs_id = o.id AND m.role = '旧')
```

`idx_relation_members_obs(obs_id, role)` を一度引くだけなので、いまの列の検査に近い形で
収まる見込みである。実測は段 2 で行う。

この決め方は、いま `mark_superseded` が持っている**先着が勝つ**（既に解決済みの行を張り
替えない）も引き継げる。部分一意索引を張れば、原子性が SQL の側に残る。

```sql
CREATE UNIQUE INDEX idx_relation_members_old
    ON relation_members(obs_id) WHERE role = '旧';
```

役割の語（旧、新、前、後、起点、版、見た、つなぎ、答え、要約、項）は種類をまたいで
重ならないので、`旧` を表の全体で一意にして差し支えない。

**想起に出さない役割は、段 4 で二つになった。** `旧` のほかに `つなぎ` がある。つなぎの
一言（「調べてみるね」）は声に出しているので、記録に無いと相手が聞いた会話とパジュが読み
返す会話が食い違う。かといって想起の候補に混ぜると、中身の無い一言が枠を食う（054 が
つなぎを記録から外した理由がこれである）。役割が「想起に出さない」を担う形になったので、
**項として持ちながら想起から外す**ことができる。

| 役割 | 意味 |
|---|---|
| `旧` | もう現行ではない（改訂・畳み込み・解決・前進の帰結） |
| `つなぎ` | 口に出したが、覚えておく中身がない |

絞りは `not_hidden` 一箇所に集まっているので、そこが見る役割の一覧が二つになる。

### `superseded_by` 列は落とす

正本を一つにする。`superseded_by IS NULL` は 18 箇所にある。

| 場所 | 件数 | 内訳 |
|---|---|---|
| `store/observations.py` | 14 | 想起の絞りが 13、`mark_superseded` の書き込みの守りが 1 |
| `diffuse_store.py` | 2 | 想起の絞り |
| `legacy/semantic_layer.py` | 2 | 想起の絞り |

想起の絞り 17 箇所は、役割 `旧` を見る副問い合わせへ書き換える。書き込みの守り 1 箇所
（`observations.py:959`）は部分一意索引が担うので、関係の口へ委譲する。

列を残して関係表の写しとする案は採らない。二つの正本が並ぶと、乖離したときにどちらが
正しいかを決める規則が要り、その規則自体が新しい複雑さになる。

性能は落ちる可能性がある。想起は最も熱い経路なので、段 2 で実測して記録する。

### 答えの逐語を畳むのをやめる

`agent.py:490-493` の畳み込みを外し、自分が答えた逐語を想起の母集合に残す。問いの逐語と
答えの逐語が両方あって初めて、細部のベクトルどうしが近接する。

会話要約は畳む側ではなくなり、粒度の粗い別の記録として並ぶ。同じ問いに逐語と要約の両方が
当たり、W の枠を食う可能性がある。段 3 で実機の W の中身を見て判断する。

## 段取り

段ごとに検証を通し、コミットする。

### 段 1：器を作る（実装済み・2026-09-06）

`relations` と `relation_members` を `migration/2026-09-06-058_relations.py` で追加し、
読み書きの口を `src/familiar_agent/store/relations.py`（`RelationStore`）に置いた。
既存の経路からは呼んでいないので、挙動は変わらない。

公開面は三つである。

- **`add(kind, members)`**：関係を一つ書き、その id を返す。`members` は
  `(観測 id, 役割, 位置)` の並びで、空なら書かず `None` を返す。ヘッダと項は同じ
  トランザクションで書き、途中で落ちたら両方を戻す。項の無い関係が残ると、関係の数が
  実際のつながりの数と合わなくなる
- **`members_of(relation_id)`**：項を位置の昇順で返す。位置を持たない項は `NULLS LAST`
  で末尾に置く
- **`relations_for(obs_id, kind=None, role=None)`**：その観測が項として入る関係の id を
  古い順に返す

想起の絞りと連なりの辿りは、この段では置いていない。使う段で問い合わせの形が決まって
から足す。先回りして置くと、実際には要らない形の口が残る。

### 段 2：`superseded_by` を関係へ移す（実装済み・2026-09-06）

**六つの書き手を全部この段で移す。** 列を落とすので、移さずに残せるものは一つも無い。
それぞれに、いま実際にやっていることの名前を付ける（種類の表を参照）。`io/oif.py:261` は
口の通しなので、呼び手が種類を渡す。

既存の辺は、どの書き手が作ったかを行から判別できない。推測で分類せず、`未分類` の種類で
移す。段 3 以降で意味の分かるものから付け替える。

想起の絞り 17 箇所と `_read_supersede_chain`（`observations.py:575-601`）の再帰を、役割
`旧` を見る形へ書き換える。`mark_superseded`（`observations.py:951-962`）は関係の口へ
委譲する。

**列を落とす前に `observations_superseded_by_backup` へ写す。** 本番の列を落とす操作は
戻せないので、`observations_removed_fillers`（054）と同じやり方で控えを残す。移した件数と
元の件数が合わなければ、マイグレーションを例外で止める。

**この段では挙動を変えない。** いま隠れている記録は隠れたまま、見えている記録は見えた
ままである。答えの逐語を畳むのをやめるのは段 3 である。

想起の応答時間は `計測_設定値根拠台帳` §28 に書いた。10,000 行・隠れ 30% で、列
30.44ms に対し関係 36.11ms（比 1.186・＋5.7ms）である。主LLM のターンが 1.7〜4.7 秒
かかるので、この差は体感には出ない。段の前後で別々に測らず、同じデータに両方の形を当てた。

実装は `migration/2026-09-06-059_move_supersede_into_relations.py` と
`store/relations.py` の追加分（`not_hidden(alias)`・`hidden(alias)`・`hide()`・種類の定数）に
ある。想起の絞りは `not_hidden` が一箇所で組み、17 箇所はそこから取る。

**計画に無かったことが三つ出た。**

第一に、**列の値そのものを読む箇所**が `IS NULL` の検索に出ていなかった。`pending_speech`
の失効判定は列の値を見ていたので、隠れているかを計算する列へ替えた。`MentalItem` の
`supersedes` は `row["superseded_by"]` を要求していたので、読み手が渡したときだけ載る形
（`row.get`）へ替えた。自己モデルの読み出しは列一覧から外した。本番にこの値の読み手は無い。

第二に、**テスト側の 93 箇所**を書き換えた。共通の口として `tests/hidden_helper.py`
（`hide`・`hidden_by`・`is_hidden`・`LIVE`）を置いた。層の振る舞いを検査する側が層に依存
すると、層が壊れたときにテストも一緒に壊れて何も分からなくなるので、素の SQL で書いている。

第三に、**旧マイグレーションを再実行して確かめる検査 8 本が対象を失った。** 019・051・
052・053 は `superseded_by` へ書くので、列が無くなると再実行できない。新しい DB では
059 より前に順番どおり当たるため、作り直しは通る。検査だけが行き場を無くったので撤去した。

### 段 3：やりとりと継起を載せる（実装済み・2026-09-06）

一つのターンが書く記録を、やりとりの関係として順序つきで記録するようにした。役割は
**起点、版、見た、答え、要約**である。設計の当初は先頭を「問い」と呼んでいたが、ターンを
起こすのは人の発話だけではない（`情動` と `機器` もある）。`[入室]` を問いと呼ぶのは事実に
反するので、位置だけを言う「起点」にした。どの種類かは記録の `direction` が持っている。

**項は時間差で揃う。** 起点はターンの頭、版と見た結果は反復の途中、答えは反復の終わり、
会話要約は背景タスクである。全部が揃うのは `_run_post_response_pipeline` の中なので、
関係はそこで一度に書く。`_finish` は `(観測 id, 役割)` の並びを渡すだけである。

**一つの並びが二つの用を賄う。** `_note_record(obs_id, role)` が控えた並びから、拡散想起の
母集合（WR）へ渡す id と、やりとりの項の両方が出る。別々に持つと、片方へ足し忘れたときに
気づけない。**起点をこの並びに載せたので、問いが WR にも入るようになった。** それまで
`_note_record` を呼ぶのは版と見た結果と答えだけで、問いだけが母集合から漏れていた。

**ただし、二つの用は区切りの規則が違う。** 母集合への持ち越しは打ち切りでも消さない
（打ち切った調査と、言い直した問いの共起は、たどる価値がある）。一方でやりとりは、打ち切り
で閉じなければならない。**やりとりは並びの一区間である**として、区間の先頭
（`_exchange_from`）を持たせ、`_close_exchange()` が区間を切り出して先頭を進める。

これを見落として実装したため、**一つのやりとりに起点が二つ入っていた**（2026-09-07 に
修正）。人に話しかけられて調べかけを打ち切ると、`_abort_investigation` は `_finish` を
通らない。並びが次のターンへ持ち越され、打ち切られた問いと新しい問いが同じやりとりに
畳まれていた。

**打ち切りの版の親は、打ち切られた求めの起点である。** `_abort_investigation` は
`_parent_id` を捨てる前に版を書く（`event_loop.py:806-811`）ので、データの側は最初から
正しく繋がっていた。誤っていたのは、やりとりの項を親からではなく「`_finish` までに控えた
並び」から作っていたことである。打ち切りの時点で区間を閉じ、その場で `record_exchange` を
呼ぶ。答えも要約も無いやりとりになるが、それが起きた事実そのものである。

**答えの逐語を畳むのをやめた。** `_run_post_response_pipeline` の `superseded_ids` 引数ごと
撤去したので、畳む道は残っていない。逐語と会話要約は、粒度の違う別々の記憶として並ぶ。

**ターンどうしは継起でつなぐ。** 前のターンの起点と今のターンの起点を結ぶ。持ち越しは
`InformationProcessing` が持つが、再起動で消える。消えたまま進むと、そこで連なりが切れて
段 4 で直近を辿れなくなるので、**起動後の最初のターンだけ** `latest_exchange_origin()` で
引き直す。毎ターン引くと、ターンごとに無駄な問い合わせが増える。

口は `ObservationMemory` に三つ足した（`record_exchange`・`record_succession`・
`latest_exchange_origin`）。関係の側は `RelationStore.latest_member(kind, role)` である。

**同じ問いに逐語と会話要約の両方が当たる。** W の枠（`workspace_max_chars`）を食うかは、
実機で W の中身を見るまで分からない。実機の宿題として残っている。

### 段 4：直近を辿る口を作る（実装済み・2026-09-07）

**続き先は、その記録を作るのに使った W の中にしかない。** W に無い id と、自分の起点は
落とす（自己ループはさかのぼりが止まらなくなる）。

**判定は軽量LLM の専用の仕事にする**（`根拠台帳` §29・2026-09-07 に差し戻し）。実装は
最初、主LLM に `say` の `follows` で名指させていたが、続きの場面の 36.1% しか返さなかった。
言い方を強めても 52.8% で、そのぶん偽陽性が 25.0% から 41.7% へ増えた。**主LLM にとって
これは五つめの仕事である**（道具を選び、応答を書き、口調を守り、記憶を申告し、そのうえで
判定する）。同じ場面で `memory_verdicts` の申告率も 31.5〜45.4% にとどまり、同じ一つの
注意を分け合っていることが読める。

判定だけをさせる軽量LLM は、続きの場面 36 回すべてで正しい id を返した。速さも 0.72 秒で
主LLM の 2.11〜2.70 秒より速く、費用は 1000 ターン 81 円である。

**判定はターンの頭で投げ、システム文を組む直前に受け取る**（実装済み）。判定が「続きでない」
なら前のやりとりをプロンプトへ載せてはいけないので、待つ必要がある。調停と並行して走らせれば
0.72 秒はほぼ隠れる。

口は `Evaluator.judge_follows(workspace_ctx, utterance)` で、返りは12桁の id か `None` である。
**12桁のまとまりを正規表現で探す。** 16進の文字を拾い集めると、地の文の `d` や `a` が頭に
付いて実在しない id ができる（「id は 0123456789ab です」が `d0123456789a` になった）。

判定が返した id は `_link_follows` が `_w_index` と突き合わせる。**W に無い id と自分の起点は
落とす。** 判定は形しか見ておらず、実在までは確かめていない。

**落ちたら繋がない。** 判定が来ないターンは新しい話の始まりとして扱う（`_settled`）。誤って
繋ぐと、関係のない会話が文脈に混ざる。ターンは止まらない。

`say` の `follows` 欄と、`(rules ...)` の一文は撤去した。

段 3 の「直前の起点へ無条件に繋ぐ」は撤去した。あれは鎖の種類を機構の側で数え上げること
になり、並行して走る本数に上限が生まれていた（会話と見回りが同じ一本に混ざる）。名指す形に
すると、鎖は**繋がった結果として現れる**ものになり、機構は種類を知らなくてよくなる。
再起動で連なりが切れる問題も、持ち回りを持たないので消えた。

`RelationStore.recent_exchanges(origin_id)` が継起を `WITH RECURSIVE` で**根まで**さかのぼる。
**上限を持たせない。** 会話はどこかで始まってどこかで終わるので、根で自然に止まる。何歩まで
と決めるのは、鎖の長さを機構の側で決めることになる。返すのは口に出したもの（起点・つなぎ・
答え）だけで、`版` と `見た` は内部の作業記録なので混ぜない。

可変部の並びは **いま → 在席 → 内部状態 → 反復 → 直近のやりとり → 作業状態**である。
「さっき何があったか」を「何を覚えているか」の直前に置く。**逐語で、切らずに出す。** W は
120 字で切るが、細部が要るからこの設計にしたので、ここで縮めると意味がない。

**辿り始める場所は、そのターンの起点ではない。** 起点はまだどのやりとりにも属していない
（やりとりを書くのは反復が閉じたあと）し、`follows` もターンの終わりに決まる。そこで
「直前に閉じたやりとりの起点」を**表示のカーソル**として持つ。繋ぐためではなく、どこから
見せるかだけのものである。辺は書かない。起動直後は空なので、最初に要るときに一度だけ
`latest_exchange_origin()` で引く。

出-f（整合チェックの繋ぎ直し）は、この口を前提にする。

**実機で確かめていないことが二つある。** W と直近のやりとりが両方載ったときの長さと、
主LLM が `follows` を実際に返すかである。後者は `memory_verdicts` と同じく、規則に書いても
守られないことがある。

### 段 5：共起を移す（実装済み・2026-09-07）

`wr_records` と `wr_record_items`（030）を共起の関係へ移した（060）。あの2表は既に
ヘッダと項に分ける形を取っていたので、種類 `共起`・役割 `項`・位置は空、という形へ
そのまま移せた。**元の2表は落とさず `wr_records_moved`・`wr_record_items_moved` へ
改名して残す。** 本番の表を落とす操作は戻せない。

**共起の検索は種類で絞る。** 一つの表に全部の関係が載っているので、絞りを落とすと同じ
ターンの問いと答え（やりとり）が共起として返ってくる。

拡散想起に手を入れる段をここまで遅らせたのは、段 2 で想起が壊れたときに、原因が改訂の
移行にあるのか拡散想起にあるのかを切り分けられるようにするためである。

**実装で三つ出た。**

第一に、`diffuse_store.cooccurring_mi_ids` は**呼び手が 0 件ではなかった**。拡散想起の
候補集め（`tools/memory.py` の `_diffuse_extend`）から使われている。撤去ではなく差し替えに
なった。計画時の検索が、複数行にまたがる import 文を拾えていなかった。

第二に、**錠を二重に取って止まった**。呼び手は既に `_db_lock` を持っており、層が取り直すと
再入できない。既に錠を持つ呼び手は接続を渡す形にした（`conn=`）。

第三に、**行が tuple でも dict でも来る**。拡散想起は素の接続を持ち回っており、層が包む
`RealDictCursor` とは違う。1列の読み出しを両対応にした。

`wr_store.py` は撤去した。純関数の `combine_cooccurring_ids`（当時 `combine_wr_ids`）は `store/relations.py` へ移した。

**測っていないことが二つある。** 移行そのものの所要時間（本番の WR は 030 以降のターン分
あり、1本ずつ書く）と、共起の検索が遅くなったかである。結合が一つ増えている。

## 影響

### 記-e は残らない

記-e は「応答した発話を閉じる」を課題としていた。この設計では閉じるという操作を置かない。
問いの逐語は想起の母集合に残り続け、答えの逐語と同じやりとりの関係に並ぶ。

### 課題8 の記-e の節に誤りがある

記-e は「閉じられていない 174 件は、答えたはずの問いがまだ答えていないものとして W に残り
続ける」と書いている。W へ浮かせる下限は `_open_ids` が返す `self._parent_id` と
`self._version_id` に掛かり、両方とも `_finish`（`event_loop.py:1451`、`1453`）で捨てられる。
ターンをまたがないので、この記述は成り立たない。

同じ節の「閉じている 347 件は、ほとんどが日次要約による」も、現行コードの説明としては
成り立たない。`_generate_day_summary`（`agent.py:1258-1300`）は `mark_superseded` を呼ばず、
day_summary の記録を書くだけである。計測が見た置換先は、いま動いていないコードが残した
過去の値である。

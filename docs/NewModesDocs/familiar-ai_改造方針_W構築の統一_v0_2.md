# familiar-ai 改造方針：W 構築の統一（v0.2）

## この文書の位置づけ

イベント駆動ループの W 構築を、設計正本 [D-想起起動] が定める1本の経路へ寄せる改造の方針
である。対象は `src/familiar_agent/loop/event_loop.py` と `src/familiar_agent/tools/memory.py`、
および `src/familiar_agent/config.py`。

設計方針は 2026-07-30 のセッションで決めた。この文書は、その設計方針を TDD の作業単位へ
割ったものである。

## 発端となった症状

`search_deferred` と `fetch_deferred` で追加調査を重ねると、前の調査結果が W から消える。
実機では、つなぎが毎回「調べてみるね」になり、前に分かったことを踏まえない応答が続いた。
同じ検索が4反復連続した記録がログに残っている（2026-07-30 20:04:31 から 20:04:42）。

## 原因

原因は2つある。ひとつは畳む処理の不正確さであり、もうひとつは W 構築が設計正本から
外れていることである。前者は後者の帰結として現れている。

`_advance_chain` は、新しい記録を書くたびに直前の生きた記録を `mark_superseded` する。
2回目の調査に入るとき、鎖の先頭は1回目の完了 O なので、意図 O がそれを畳む。畳む相手を
「鎖の先頭」という間接で決めているため、畳んではいけないものを畳んでいる。

より深い原因は、W の組み立てが2つの経路に分かれていることである。想起で拾った記録は
候補集合の union と5軸採点を通るが、ループ自身が O へ書いた記録（意図 O、完了 O、答えの O）
は、採点を通らず手組みの文字列として W へ連結される。そのため、記録が W に載るかどうかが
「畳むか畳まないか」という別の仕組みで決まり、優先度の計算がどこにも効かない。

## 設計正本との乖離

設計正本は次を定めている。

- **`設計図_Mermaid_v0_68.md:26`（[D-想起起動]）**：入口だけが trigger 固有で、O に乗った
  後は共通の流れ（O から 根づき、W 構築の5軸採点、調停）で1本にする。5軸の重みは
  trigger 種別で決める。この方針を書いた時点では trigger を3つに集約すると定めていたが、
  S2 の実装に合わせて4つへ改めた。
- **`課題5_パラメータ仮案_v0_37.md:92`**：W 載せ上限 $K$＝7（min_score を超えた候補の
  上位・最大 $K$ 件を W へ）。
- **`課題5_パラメータ仮案_v0_37.md:93`**：一次絞り件数 $N$＝50（軸あたり）。$N \ge K$。
- **`課題5_パラメータ仮案_v0_37.md:184`**：open 保持 $a_{open}$＝1.0（open の間だけ導出値に
  下限を課す）。
- **`課題5_パラメータ仮案_v0_37.md:327`**：5軸の重みは trigger ベース。基底
  $(w_r, w_t, w_e, w_a, w_p) = (1, 1, 1, 1.5, 1.0)$。会話入力は $r$・$p$ 寄り、情動発火は
  $e$・$t$ 寄り、知覚イベントは $r$ 寄り。具体値は仮値。

実装はこの5点すべてで正本から外れている。

| 乖離 | 正本 | 実装 | 出所 |
|---|---|---|---|
| 1 | 5軸の重みは trigger 種別で決める | Config 固定。全 trigger で同じ値 | `memory.py:840-844` |
| 2 | 候補 $N$、床、上位 $K$ 件の2段 | $K$ が存在しない。`recall_n`＝5 の1段 | `memory.py:878` |

| 5 | $a_{open}$ で open な記録を高く保つ | 未実装 | grep 0件 |

`a_open` は実装に存在しない（`grep a_open` が0件）。

## 決めたこと

**trigger は4つとする。** 発話、機器、情動、完了である。正本は当初3つに集約していたが、
完了の到着が次の反復を起こす実体は実機で必要だった。正本の側を4つへ改めた（設計図 v0.68・
用語一覧 v0.43）。

**trigger 別の重み。** 値は仮値であり、Config から差し替える。

| trigger | 手がかりの中身 | $w_r$ | $w_t$ | $w_e$ | $w_a$ | $w_p$ |
|---|---|---|---|---|---|---|
| 基底（正本） | — | 1.0 | 1.0 | 1.0 | 1.5 | 1.0 |
| 発話 | 人の言葉、在席者、mood | 1.5 | 1.0 | 0.8 | 1.5 | 1.5 |
| 機器 | 入退室の事実 | 1.2 | 1.2 | 0.8 | 1.5 | 2.0 |
| 情動 | 中身なし | 0.5 | 1.5 | 1.5 | 1.5 | 1.0 |
| 完了 | 届いた結果の本文 | 1.5 | 1.5 | 0.5 | 1.5 | 1.0 |

**採用値は、このプロファイルに $\pm$ 幅の一様乱数を足したものである。** 値を仮値のまま固定
すると、どの向きへ動かせばよいかが分からない。反復ごとに少し振り、採用値と結果を INFO へ
残して、実挙動から良い値を選べるようにする。幅は**軸ごとに別で、trigger 共通**の絶対値
である。

| 軸 | 幅 |
|---|---|
| $w_r$ | 0.3 |
| $w_t$ | 0.1 |
| $w_e$ | 0.2 |
| $w_a$ | 0.3 |
| $w_p$ | 0.1 |

幅 0 の軸は動かない（テストと再現確認はこれで止める）。重みが負になると意味が反転するので
0 で下げ止める。

$w_r$ は関連ゲートの指数であり、残る4つは加算部 $M$ の加重平均係数である。式は
`score = r^{w_r} \times M`、$M = (w_t t + w_e e + w_a a + w_p p) / (w_t + w_e + w_a + w_p)$
（`memory.py:167-186`）。$r \in [0, 1]$ なので、$w_r$ を上げると関連の薄い候補がより強く
罰される。加算部は分母で正規化されるため、比だけが意味を持つ。

発話では人の問いという信頼できる手がかりがあるので、関連を厳しく要求する。誰に向けた話かが
効くので $w_p$ を上げる。機器では主題が「誰が入ってきたか」なので $w_p$ を最も高くする。
情動では手がかりが中身を持たないため、関連を厳しくすると何も浮かばない。完了では手がかりが
結果本文であり関連が信頼できるので厳しくし、調べた結果の選別に気分を効かせる理由がないので
$w_e$ を下げる。

**完了の反復では、トリガ O にも $a_{open}$ を課す。** 完了の反復の手がかりは結果本文なので、
元の人の問い（トリガ O）の $r$ が低くなりうる。「リバプールの試合どうだった？」と試合結果の
本文で、語彙が重なるとは限らない。$w_r$＝1.5 で関連を厳しくすると、何のために調べていたかが
W から落ちる。時間軸で拾う道もあるが、時間軸は「数秒前のもの全部」を拾うので無関係な記録も
一緒に上がる。求めが閉じるまでトリガ O を open 扱いにし、$w_a$＝1.5 の重みで浮かせる。

**W の量は件数と字数の両方で抑える。** $K$＝7 件（正本）と、W 全体の字数枠 40000 字
（Config `workspace_max_chars`）である。字数枠の下限は、1つの求めで届きうる完了 O が全部
同時に全文で載る大きさから決まる。`event_max_iterations`＝5 で5反復目は `capped` により
調べられないので、1つの求めで届く完了 O は最大4件である。完了 O 1件の上限は 8192 字
（`completion_content_max`、bge-m3 の入力上限に合わせた値）なので、4件で 32768 字となる。
40000 字はこれに余裕を持たせた値である。

**枠を超えたときは、スコアの低い件から丸ごと落とす。** 1件の途中で切らない。切ると、
調べた結果の枕だけが残って中身が消える。実機では、2日前の完了 O が想起欄に上がったとき、
`「目の前を見る」を see で調べた結果が届いた：` という枕だけが W に載っていた（現行の
120 字の切りによる）。

**取込 O は候補集合に入れる。** 手がかりは取込の content そのものなので、コサインがほぼ 1.0 で
1位に来る。これは枠を食っているのではなく、いちばん重要なものが1位に来ている状態である。

**畳む処理は2箇所に整理する。** 意図 O は何も畳まない。完了 O は自分の意図だけを畳む
（`intent_id` は完了キューが運んでいる）。求めが閉じたときは `close_with_children` が親と
全子（意図 O と完了 O）を1文で畳む（`store/observations.py:918-922`）。

## 注意点

1. **DB のスキーマ変更は無い。** $a_{open}$ は採点時に計算し、open な id はループが渡す。
   マイグレーションは不要である。
2. **実測の無い帯に入る。** 調停プロンプトの実測は合計 8619 字までであり（70件、4k 字台で
   平均 1.07 秒、8k 字台で 1.13 秒）、字数枠 40000 はその外側にある。調停の時間切れは 5.0 秒
   なので現状は4倍以上の余裕があるが、40000 字の帯では測っていない。実機で長さと秒数を測り、
   台帳へ記録する。
3. **`recall_overfetch_factor`（3）と `recall_overfetch_cap`（20）は $N$＝50 と役目が重なる。**
   一次絞りが $N$ になれば過剰取得は不要になるので撤去する。
4. **`format_for_context` の他の呼び出し元の挙動は変えない。** `memory.py:1186`（Coalition
   提案）は別経路であり字数枠を持たない。切らない指定は引数で受け、既定は現在の 120 字の
   ままにする。
5. **`said`（言ったつなぎ）と `held`（保留していた発話）は統合しない。** どちらも O にあるが、
   `held` は `pending_store` が鮮度と配達を管理しており、想起とは別の規則を持つ。手組みの
   まま残し、理由をコメントに書く。

## 作業単位

各単位の後で人間の確認を挟む。

### S1：想起を2段にし、床を通す

`recall()` の `n` を、軸あたりの一次絞り件数 $N$（既定50）と W 載せ上限 $K$（既定7）へ分ける。
Config に `recall_primary_n` と `recall_k` を新設する。`event_loop.py:874` と 919 の
`recall_async` に `min_score`（0.05）を渡す。`recall_overfetch_factor` と
`recall_overfetch_cap` を撤去する。

RED は、完了 trigger の反復で `by_vector` に $N$＝50 が渡り、W へ返るのが最大7件であることを
確かめるテストである。現在は両方 5 なので、50 を期待して 5 が来る形で落ちる。

既存テストのうち `test_recall_min_score.py`、`test_recall_threshold.py`、
`test_memory_recall_metadata.py` が `n` の意味に依存していないかを確認し、必要なら期待を
$N$ と $K$ へ書き分ける。

### S2：trigger 別の重みプロファイル

Config に4プロファイルを持たせ、`recall()` へ重みを渡せるようにする。省略時は現在の Config
値を使い、挙動を変えない。`_iterate` が `_origin_kind` からプロファイルを選んで渡す。

RED は、情動起点の反復で $w_r$＝0.5 が採点に渡ることを確かめるテストである。現在は 1.0 が
渡るので落ちる。

プロファイル定義の直上に、$w_r$ が指数であり上げると関連の薄い候補が強く罰されること、
残る4つは加重平均なので比だけが意味を持つことをコメントで書く。これが無いと値の向きを
逆に直される。

### S3：open な記録の活性下限

`recall()` に `open_ids` を足し、採点時に $a = \max(\text{導出}, a_{open})$ とする。$a_{open}$ は
Config（既定 1.0、範囲 0.5〜2.0）である。ループが渡す open な id は、生きている意図 O と
トリガ O である。

RED は、完了の反復でトリガ O が W に載ることを確かめるテストである。手がかりが結果本文で
$r$ が低いため、$a_{open}$ が無ければ $K$ の外に落ちる。落ちる側を先に見る。

トリガ O を open 扱いにする理由をコメントに書く。

### S4：W の組み立てを候補集合へ統合

`_iterate` の `exclude_ids`（872行）をやめ、取込 O を候補に入れる。`_compose_workspace` から
`looked_up`、`waiting`、`chain_head_content` の手組みを外す。`format_for_context` に
1件あたりの字数上限を引数で受ける口を足し、W からは切らない指定で呼ぶ。字数枠
（Config `workspace_max_chars`、既定 40000）を課し、スコアの低い件から丸ごと落とす。落とした
件数を info でログする。

RED は、2回続けて検索した反復で1回目と2回目の完了 O が両方 W に載ることを確かめるテストで
ある。現在は1回目が supersede されて消えるので落ちる。

既存テストのうち `test_workspace.py` と `test_event_loop.py:985`（`_chain_head_content` を
参照）が影響を受ける。985 の主張（つなぎが W の材料を押し出さない）は意図を保つ形へ書き
換える。

### S5：畳む処理の整理

`_advance_chain`（1186行、意図 O）から supersede を外す。`_intake`（416行）を
`mark_superseded(intent_id, obs_id)` の直接呼び出しへ変える。`_finish` のまとめの MI の
content を、答えと調べた一覧と結果の抜粋を持つ形にする。

RED は、意図 O を書いたときに `mark_superseded` が呼ばれないことを確かめるテストである。

既存テストのうち `test_event_loop.py:185`（`test_loop_records_form_a_single_chain`）は期待が
`[("obs1","obs2"),("obs2","obs3")]` であり、新しい期待は `[("obs2","obs3")]` だけになる。
テスト名と docstring も実際の姿へ改める。`test_event_loop.py:385`（完了が意図を畳む）は
そのまま通る。`_abort_investigation` は既に `close_with_children` で畳んでおり、
`_chain_head_id` を捨てる処理を新しい入れ物へ合わせるだけである。

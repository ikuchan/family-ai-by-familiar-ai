# familiar-ai 設計方針：求めの版チェーン（v0.2）

## この文書の位置づけ

`superseded_by` が2つの意味を兼ねている状態を解き、求め（人からの問いや内的な促し）の進み
ぐあいを1本の版チェーンで表す設計を定める。W 構築の統一（`改造方針_W構築の統一`）とは別の
題である。あちらは「W に何をどう載せるか」、こちらは「記録どうしの版の関係をどう表すか」を
扱う。

## 原因

用語一覧は **版超越（supersede）** を「版履歴専用の更新方式。新版が旧版を無効化し版チェーン
（履歴）を残す。**解決には使わない**」と定めている。ところが実装の `close_with_children` は、
求めが決着したときに親（人の発話）と全子（意図 O・完了 O）へ、まとめ役の記録の id を
`superseded_by` として書き込む。

これは版の更新ではない。意図 O は「調べてと頼んだ」という別の出来事であり、完了 O は
「これが届いた」という別の出来事である。人の発話に至っては話者すら違う。したがって
`superseded_by` が「版が新しくなった」と「この求めは決着したのでもう想起に出さない」の
2つを兼ねている。

意味が2つあると、畳む側が何を持つべきかが定まらない。版の更新なら新版が旧版の内容を含むのは
当然だが、決着の印なら内容を持ち込む必要はない。実際、畳む側は「自分が答えた：…」という
調査と無関係な記録であり、畳まれた内容を辿る道がどこにも残らなかった。

正本 [D-単一想起] は、解決を別の形で定めている。**フルLLM が充足または失敗を宣言して解決**し、
closed になった記録は「浮かばないので自然に無視」される。想起の重みの一項が未解決であり、
候補から機械的に外すのではない。実装はこの機構を持たないまま、`superseded_by` で代用している。

## 対応

**求めを1本の版チェーンとして表す。** 各版が求めの状態であり、content にはその時点の全体が
書かれる。版が進むとき、新しい版が前の版を supersede する。これは版履歴そのものなので、
`superseded_by` の定義と一致する。

```
版1  「昨日の天気覚えてる？」と聞かれた
       ↓ supersede
版2  「昨日の天気覚えてる？」と聞かれ、1番：search「昨日 天気」を起動中
       ↓ supersede
版3  「昨日の天気覚えてる？」と聞かれ、1番の結果が届いた：…
       ↓ supersede（まとめ知識を作る場合）
版4  まとめ知識
```

`close_with_children` は撤去する。親子のファンアウトではなく1本の鎖になるので、まとめて畳む
操作そのものが要らない。

### 並行する調査

調査は並行しうる。`deferred_search` と `deferred_fetch` はいずれも同時実行の上限が3で、
飛行中の調査を列で持っている。1本の版チェーンは「現在の版が常に1つ」を前提にするため、
素朴に作ると2つの完了が同じ版を supersede しようとして鎖が分岐する。

**鎖は分岐させない。** 調査ごとに**求めの中の通し番号**を振り、版の content に列挙する。

```
「今日の天気は？」と聞かれ、1番：search「今日 天気」／2番：fetch「example.com/…」を起動中
       ↓
「今日の天気は？」と聞かれ、1番の結果が届いた：…／2番：fetch「…」は起動中
```

状態は「求め」の状態であって個々の調査の状態ではない。3件飛んでいても、求めの状態は
「調査中」ひとつである。届いた完了は通し番号で対応づく。

通し番号が要るのは、並行する調査を見分けるためである。求めをまたいだ突き合わせは不要なので、
求めの中の通し番号で足りる。完了キューの要素にも通し番号を載せる。

### 同じ語は二度と調べない

通し番号を語から引けるようにするには、**1つの求めのあいだ語が重複しない**必要がある。
`deferred_search` と `deferred_fetch` は、同じ意図の調査が飛行中・保留中なら投げない
（軽量LLM が言い換えまで見て判定する）。ところが `recall`・`see`・`look` は素通りで、実機
では同じ `recall` を4反復続けて投げた（語は MD5 まで一致）。4回とも同じ記憶を取ってきて、
4反復ぶん無駄になった。

**この求めで一度調べた語は、二度と調べない。** 判定はループ側に置き、語の一致だけを見る
（言い換えの判定は deferred 側が持つ）。`recall` は指定した語で自分と在席者の記憶を横断して
探すツールで、DB を引くだけである。同じ語で引き直しても結果は変わらないので、取り直しに
意味がない。

止めた調査は「すでに調べた」旨を**完了として積み**、反復を続ける。投げずに黙って帰ると、
完了も時間切れも来ないまま飛行中の数だけが残り、駆動体が待ち続ける（`deferred` が投げられ
なかったときと同じ形にする）。

これで語からの引き当てが一意になる。`deferred` の完了は `sink(語, 結果)` と語で届くので、
ツールの API を変えずに番号を対応づけられる。

### 打ち切り

話しかけられて調査を打ち切ったときも、鎖の一つの版として「打ち切った」を載せる。中断は
求めの状態のひとつだからである。

### 発話の記録は鎖の外

人の発話は、発話の記録としてそのまま残す。版1（求めの状態）とは別の記録である。検索を
始めたときは「検索を始めた」を**一度だけ**追記し、埋め込みを作り直す。何を調べているかは
鎖の側が持つので、発話の記録が持つ必要はない。二重に持つと、どちらが正かが曖昧になる。

追記のたびに埋め込みを作り直すのは、content とベクトルの食い違いを残さないためである。
`content` を書いた後に足すと、想起はベクトルで探すので足した文言が検索に効かず、W へ出る
文面だけが変わる。実測で「500字の埋め込みと挿入」は 26ms であり、LLM 呼び出しが1ターン
10.5 秒のうち 10.2 秒を占めることに比べれば誤差である。

自分が答えた記録も鎖の外に置く。会話要約がこれを畳む経路は現状のままとする。

### 畳む記録の先頭を持ち込む仕組みは要らない

一度は、畳むときに相手の content の先頭120字を印つきで持ち込む仕組みを入れた。これは畳む側が
「何を畳むか」を考えずに書かれていることへの当て木だった。版チェーンでは各版が前の版を知った
うえで content を組み立てるので、機械的な継ぎ足しは不要である。むしろ同じ内容が二重に入り、
content が膨らんで埋め込みも薄まる。

## 決めていないこと

**版を進める判断を誰がするか。** 正本は解決の宣言をフルLLM と定めるが、開始側については明記が
見当たらない。実装では調停（軽量LLM）とフルLLM の両方が検索の開始を決めており、機械判定は
入っていない（条件として反復上限だけが効く）。**この判断は変えない**。

**まとめ知識の MI を作る条件。** 作らない求め（調べずに答えた場合など）では鎖が「完了」で
止まる。作る・作らないを何が決めるかは定めていない。

**closed 状態と未解決の重み。** 正本は「未解決」を想起の重みの一項と定めるが、実装の5軸
（関連・時間・感情一致・根づき・在席相関）にその項は無い。版チェーンは supersede の意味を
正すが、closed 機構そのものは実装しない。

## 影響

- `close_with_children` を撤去する。呼び出し元は `_finish` と `_abort_investigation`、および
  背景の永続化の3箇所である
- 完了キューの要素に通し番号を足す
- 同じ語を二度調べない判定を `_dispatch_lookup` の入口へ置く
- 版の content を組み立てる処理を新設する
- 発話の記録への追記と、埋め込みの作り直しの経路を作る

## 改訂履歴

> v0.2：**同じ語は二度と調べない**を追記した。通し番号を語から引くには、1つの求めの
> あいだ語が重複しない必要がある。`deferred` は自前で止めていたが `recall`・`see`・`look` は
> 素通りで、実機で同じ `recall` が4反復続いた。止めた調査は完了として積み、反復を続ける。
> 番号が要る理由も「同じ語の区別」から「並行する調査の区別」へ改めた。

> v0.1：新規。`superseded_by` が版履歴と解決の2つを兼ねている状態を解き、求めを1本の版
> チェーンで表す設計を定めた。並行する調査は求めの中の通し番号で content に列挙し、鎖は
> 分岐させない。畳む記録の先頭を持ち込む仕組みは要らなくなる。

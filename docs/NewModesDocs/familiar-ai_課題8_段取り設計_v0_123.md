## 2. 段取りの原則

- **recall 一本化が起点**：旧 cosine 純積と新5軸を**並走させない**。新スコアラへはクリーンに切り替える（フラグで旧/新を持つにしても、同時に二重採点しない）。
- **現行先行（Phase 0）は新アーキと独立**に進む（BUG-1・bge-m3）。再測定はこの後。
- **基盤（O/MI データモデル）が先、recall 一本化が次**：5軸は O の上で動くため、O モデルが無いと意味を持たない。
- **旧系統の撤去は最後**：新経路が通って実証されてから、grep 残存ゼロを完了条件に撤去する。
- **DB 変更はマイグレーション＋テスト＋ロールバック**を各フェーズに含める。カラム・ストア廃止は「旧名 grep で0件」を完了条件にする。
- **一項目ずつ**：各フェーズはさらに小ステップに割り、ステップ毎にユーザー確認。全体テストは `./scripts/run_tests.sh` で自分（Claude Code）が回す。

**根拠**

2026-07-20 に3件の不具合を見つけた。`say()` で話したターンが永続化されない（`run()` 795行の約590行目に埋もれた条件式）、感情語の一致を辞書サイズで割っていて値踏みゲートを越えない（`appraisal.py`）、観測 `timestamp` が9時間ずれる（`memory.py` の1行）。関数の長さが直接の原因なのは1件目だけで、3件に共通するのは**誰も端から端まで確かめていなかったこと**である。最後の書き込みが 2026-06-29 で、3週間気づかなかった。よって不変条件を先に置く。

**順序**

1. **生存確認の不変条件**。分解の安全網。これ無しに2ファイルを切り刻むのは、壊れても分からない状態で大工事をすることになる。粒度は着手時に詰める。

### Phase 5：挙動（反復抑止・REST・拡散想起）
- 内容：[D-反復出力]（1反復1出力）、REST（近重複統合・内省・自己エピソード supersede・per-person 蒸留）、WR 拡散想起（memory_links 代替）。
- 依存：Phase 1（O/T）＋ Phase 2（recall）。BUG-1 の冪等化と整合（恒久の反復抑止）。
- テスト観点：同一意図の再発火が止まる／REST が日次 O を正しく統合／WR の seed と想起 MI 選択。
- **WR 拡散想起は W 想起の再帰化として設計し、旧 ToM ツールの第二 W を吸収する**：W が想起した MI が、その場にいない人の話を含むとき、その人を種にさらに想起して MI を W へ足す。1回の想起で閉じず、想起が想起を呼ぶ再帰である。旧 ToM ツール（撤去済み）は内部で独自クエリの想起を叩いており、これはターンの W とは別の第二の W を立てているに等しかった。この第二 W は WR の再帰想起が担うべきもので、新ループでは不在の人の考慮を WR へ畳む（ToM 自体は撤去済みで、現行は一人称 CoT が W の在席者と想起 MI の人を想像する）。
- **ToM のもう一方の働き（他者の心の想像）は「W を消費する一人称 CoT」に置き換え、WR と相互再帰で噛み合わせる**：応答の前に、いま W の文脈に出ている人それぞれの気持ちと望みを一人称で想像し、その上で自分として一人称で答える（三人称の視点分析レポートで応答を置き換えない）。この CoT は W の**下流**に置き、対象を固定の人リストでなく「W の文脈に出る人」で定義するので、W の作り方に依存せず、WR で W が深まればそのまま対象が増える。**想像が新たな想起を呼ぶ相互再帰（想像→その人を種に再帰想起→増えた人も想像）は上流の WR 側に置く**。この一人称 CoT 自体（対象は当面 W の在席者＋想起 MI の人）は Phase 2 の知覚が入った後に先行実装でき、WR が入れば自動で深まる（先行実装しても作り直しにならない）。

- テスト観点：撤去後に新経路だけで全機能が成立する回帰。
- 撤去できなかったもの：`prediction`／`concern_engine`／`exploration` は `_run_post_response_pipeline` 経由で新経路が使う。`self_state` は後に**撤去した**（書き込みだけが生きており、読み手が居なかった）。`workspace.py` は `Coalition` が生きているのでファイルを残す（2026-09-10 に **`coalition.py`** へ改名。`loop/workspace.py` と名前が重なったため）。

### 番号の付け方

課題は**群を表す漢字1文字＋英小文字**で識別する（`記-a`・`知-c` など）。数字を使わないのは、設計図の「課題 N」と混ざるためである。英数字（`A-1` 等）を避けたのは、本書の「段階A」「B-1」と衝突するためである。

課題をさらに段へ切るときは、**いろは**を足す（`記-a-い`・`記-a-ろ`）。ここでも数字を避けるのは同じ理由である。

#### 背景で投げる。ただし打ち切りでは消さない

申告は答えを出したあとの後片付けなので、発話を待たせる理由がない。**`_verdict_tasks` という
別の集合に置く**——`_abort_lookups()` は `_background_tasks` を全部 cancel するので、そこへ
入れると言い直されたときに申告が消える。**主LLM の返りは古くなるが、申告は「実際にその記憶を
使った」という事実で、あとから古くならない。**

**投げるときに写して閉じ込める**（`dict(w_id_map)` と `mem`）。走っているあいだに次の反復が
来れば、ループの対応表も面も作り直されている。

#### ③ 申告が当たる面を、想起した面へ揃えた（同時に直した）

**これは非同期にする前から在った食い違いである。**

| | 使っていた記憶オブジェクト | 書く面 |
|---|---|---|
| 想起（W を組む） | `agent._active_memory()` | **話者の面** |
| 申告（`apply_verdicts`） | `agent._memory` | **`__self__` の面** |

`situated_memories` は人ごとで、`apply_verdicts` は `UPDATE ... WHERE person_id = viewpoint`
を打つ。話者が同定されていない場面では両方 `__self__` なので一致するが、**顔認識か声紋で
話者が決まった場面では0行に当たり、申告が効かない。**

#### 症状

|---|---|

#### 環-f-い-1：順序づけが3箇所に散っていた（2026-09-11 完了）

#### 装置が event loop より長生きする（同時に見つけて直した）

`asyncio.Queue` は**最初に使った loop に縛られる**。`asyncio.run` を2度呼ぶ形（テスト）や
GUI が loop を作り直す形では、次の loop で `is bound to a different event loop` が出続ける。

**旧コードでは見えなかった。** `asyncio.wait` の中で例外になるので毎回 await を挟んで
空回りしていた。1本にすると `await self._triggers.get()` が**同期的に投げる**ので、await を
挟まない密な繰り返しになり、**event loop ごと止まった**（テストがハングして露見した）。

直したのは2つ。**loop が変わったら中身を移して待ち行列を作り直す**（`_ensure_driver`）。
**駆動体は例外のあと必ず一度譲る**（待つ前に投げる例外でも密な繰り返しにしない）。

#### 蒸留の設計（記-a-ろ・2026-07-29 決定）

**内省はツールを持ったエージェントとして動く**（2026-07-29 決定）。蒸留だけでなく棚卸しや自己調整も担うので、仕事ごとに呼び分けるのではなく、1つのセッションの中でまとめて片付ける。LLM の呼び出しは1回では済まず、ツールを呼ぶたびに往復する（**6〜10 回程度**）。内省は1晩に1回なので、会話（1ターンで2〜3回・1日に何十ターン）に比べれば総量は小さい。

**専用のループを書く。** 既存の `event_loop.py` は「1反復1出力」で発話を前提に組まれており（配信ゲート・つなぎ・W の組み立て）、発話しない内省とは噛み合わない。

| ツール | 役目 |
|---|---|
| 記憶を読む | 蒸留の材料（前回の内省以降・下記の2段で絞ったもの） |
| 記憶を畳む | `mark_superseded`。**何を畳むかは LLM が選ぶ** |

| 調停の所要時間を見る | ログを集計して**数字で**返す（分位点・件数・時間切れの回数） |

| 畳む対象の選び方 | **LLM に選ばせる**。何を残すべきかは意味の判断で、機械の指標では決められない |
| 可逆性 | `mark_superseded` のみ（元のデータは残る）。戻す操作は作らない |

**件数の上限は設けない。** 上限で切るより、軽い O を外すほうが筋が良い（切ると、その日の後半だけが落ちるような偏りが出る）。

**既存の日次要約は起動を移す。** `_generate_day_summary` は「アプリの終了時にその日の分を作る」形で動いており（`agent.py:2456`）、日次の内省として回っているわけではなかった。終了時の生成は撤去し、**過去日の穴を埋める backfill は残す**（内省が起きなかった晩の埋め合わせに使える）。

#### Config 自己調整の器（記-a-に の一部・完了）

値の優先順位は3段。**env（人が明示）> agent_state（内省が調整）> Config の既定。** 人が env に書いた値が always 勝ち、設計の「人の設定は変えない」を順序で満たす。

**範囲を登録した値だけを調整できる。** 登録が無ければ拒否する。`rate` や `theta_fire` のような式の骨格を内省が動かすと、蓄積や発火が壊れる。**接続情報は常に拒否する**（API キー・ホスト・認証・URL・デバイス id の 18 フィールド）。書き換えられると機器へ繋がらなくなり、`agent_state`（DB）に入るので `.env` を見ても原因が分からない。

いま登録したのは `MemoryConfig.distill_min_a0`（既定 0.47・範囲 0.20〜0.70）の1件だけである。

**調停の時間切れも自己調整の対象にする**（記-a-に・2026-07-29 決定）。`AgentConfig.arbiter_timeout_sec` を **範囲 1.0〜10.0** で登録する。1.0 未満だと普通の会話（0.93〜1.10 秒）すら間に合わず常にフルへ倒れ、10.0 を超えると時間切れのときの遅延が実用に耐えない。

**値は LLM が判断する。** ただし材料は機械が渡す：ログから「調停 X.XX 秒」「調停が遅れて返った：X.XX 秒」を拾い、**集計した数字**（件数・中央・p90・最大・時間切れの回数）をツールが返す。生のログ行を渡さないのは、数百行から分位点を数えるのが LLM に向かないためで、設計の「機械が測り LLM が提案する」切り分けにも沿う。**ログは 14 日で消える**ので、それより長い傾向は追えない。**内省が値を提案する部分は記-a-に で足す。** 蒸留を回して分布が見えてから決めるほうが確実で、いま作ると根拠のない値を根拠なく動かすことになる。

### 知-a（見る・首を振るをループへ繋ぐ）

`tools/camera.py` の `see`（撮って見る）と `look`（ONVIF PTZ で首を振る）は実装済みだが、イベント駆動ループの動作の表 `_ACTIONS` に無く、**新しい系統から呼べない**。旧 `run()` には繋がっているので、既定を反転した時点（環-a 段階5）で目と首が落ちたことになる。表に2行足して繋ぐ。

**`recall` と同じ扱いにした**（実装済み）。`recall` も同期で結果が返る動作で、`_run_lookup` の中で実行して完了キューへ積む。同じ経路に乗せれば 1反復1出力 が保たれる。あわせて、撮った画像を VLM（`extract_entities`）に通して**見えたものを言葉にして完了へ載せる**。これを通さないと「撮った。以上」で終わる。詳細は `イベント駆動ループ`。

**`look` は相対のまま繋いだ。** 設計が定める絶対 pan/tilt と定点は、在席マップと norm と見回りが共有する構造なので 知-c で扱う。

### 知-b（在/不在の層）の内訳

用語一覧が定める**二層**（在/不在＝T(G)・連続、誰か＝I・必要時）のうち、**在/不在の層**を作る。この層は identity を要しないので、顔と声の登録（知-d）を待たずに実機で確かめられる。

現状は在/不在の層が実装されていない。顔の照合はギャラリーとの比較なので、**未登録の顔・顔なし・モデル無しがすべて同じ「該当なし」に潰れる**。「顔は見えるが誰か分からない人」を表せないのは、この潰れの帰結である。

- **在/不在の判定**：設計は YOLO 由来と定めており、照合を使わない。登録が無くても「誰かが居る」「居なくなった」が動く。
- **未知の在席者を表せない**：扱えるのは既知の人物だけで、「顔は見えるが誰か分からない人」に相当する表現がない。
- **`_present_ctx` の三者混在**：この関数は在席と身元を分けずに組んでいる。情報源は、PMM の在席（InsightFace の identity であって設計が言う presence ではない）、自己申告（`/speaker`・`[名前]`）、直近に話しかけられたという痕跡、の3つ。**在席は T の presence レジスタから、身元は I の解決器から**取り、この関数は表示用に組むだけの薄い関数へ戻す。証拠の種類（顔・声紋・自己申告）と確信度を、身元に添えて持てるようにする。
- **起動の順序**：`/speaker` はコマンド処理で即座に返るため、その時点では T がまだ起動していない。最初の発話で T が起動し、初回走査で既に居る人を見て「起動直後の1回目は差分を取らない」規則に当たるので、**`/speaker` を最初に打つと入室イベントが立たない**（先に一言話せば立つ）。エージェントの起動時に I と T を起こすのが対処。
- **`unconfirmed` のときに丁寧語にならない**：`ME.md` は「相手が分からないときは大人として扱い丁寧に話す」と定めるが、話者が `unconfirmed` のときは効かず、入力の文体を真似る。名前が入っているときは効く。原因は未特定。
- **会話経由の入退場**：`PersonTool`（`note_person_arrived`／`note_person_left`）はエージェントに登録されていない（`grep` で0件）。登録すれば LLM が「◯◯が来た、帰った」を記録でき、カメラが無くても在席が動く経路になる。QD の退室イベントは実装とテストがあるが**実機で一度も通っていない**ので、その確認にも使える。

### 環-b（保留していた発話を配る起点）

在席がゼロから立ち上がった瞬間だけ配る。いまその瞬間を作れるのは `/speaker` だけで、在席が正しく上下しないと配れない。知-b で在/不在が動けば、実機で確かめられる。

### 知-c（昼夜の見回り）

ユースケース③ が定める、定点を巡って様子を見る動き。首を振ること（知-a）と、定点ごとに人が居るかを見ること（知-b）の両方が要る。

### 知-d（顔と声の登録）

登録に応じられる人が揃うまで着手できない。この課題が済むまで、**誰か**の層と、それに依存するものは動かない。

- **登録の入口**：顔と声の登録を GUI／CLI から行えるようにする。認識の載せ替え自体は実装済み（InsightFace(ArcFace) 顔＋ECAPA-TDNN 声・GPU 実行・`presence_watcher` が `person_arrived`／`person_left` へ結線）で、残るは登録の入口と実際の登録。
- **p 軸（在席者相関）の実挙動**：スコアラの結線は実装済みで、在席入力が埋まればそのまま効く。相関の相手が特定できないと実挙動を確かめられない。
- **`unconfirmed` のときに丁寧語にならない**：`ME.md` は「相手が分からないときは大人として扱い丁寧に話す」と定めるが、話者が `unconfirmed` のときは効かず、入力の文体を真似る。名前が入っているときは効く。原因は未特定。この症状自体は 知-b で扱えるが、直ったことの確認には相手を変えられることが要る。
- **人に合わせた発話の実機確認が未了**：`ME.md` は丁寧さを相手で決める（大人にはですます、子どもには打ち解けて、分からなければ丁寧に）と定め、話者は `_present_ctx` 経由でプロンプトへ渡り、`/speaker` はイベントループ経路でも効くようになった。**ただし、相手を変えて口調が実際に変わることは実機で確認できていない**。大人と子どもの双方で確認する。
- **一定時間で忘れる在席**：MI の想起に駆動される在席（活性の派生ビュー）は、記憶が人に紐づくこと（D-rel＝知-e）に依存する。知-e の後に、どちらの層が寿命を持つかを決める。

### この過程で掘り当てた不具合（設計になかったもの）

新ループの実機確認から、想起そのものに関わる欠陥が出た。いずれも**現行 `run()` にも効く**。

- **絞り込み付きベクトル検索の取りこぼし**：HNSW が候補を集めた後に `person_id`・`superseded_by` の絞り込みが当たるため、母集合 2707 件でも候補が 0〜1 件しか残らないことがあった。接続時に `hnsw.iterative_scan = relaxed_order` を入れて解消（計測台帳 §13）。
- **取込 a0 の歪み**：同根で `content_novelty` の近傍も取れておらず、a0 が両方向に狂っていた。マイグレーション `2026-07-25-031` で一括再計算（計測台帳 §14）。
- **store の I/F**：重複スキップ時に**実在しない id を返していた**（supersede の宛先がどこも指さない）。`materialize_save_event` が id を返す形へ変え、`mark_superseded` は先着勝ちにした。
- **想起の例外**：コードの誤り（`TypeError` 等）が `[]` に化けて「0件」と混同されていた。degrade と伝播に分けた。
- **想起の候補集合が1軸だけだった**：設計 [D-想起合成] は**多軸 union 一次絞り**（重み>0 の各軸で `ORDER BY … LIMIT N` して UNION）を定めているが、実装は関連軸（`by_vector`）しか作っていなかった。新しさは候補に入ったあとの並べ替えにしか効かず、直前の会話が候補にすら入らない。`by_time`（基準時刻に近い順）と `by_emotion`（いまの気分に近い順・`emotion_vec` の HNSW）を足して union（活性軸は導出値のため使わないと決定）。**軸はすべて揃った**。乗算ゲートは触っていない（直近なら $M\approx0.7$ で、関連が低め $r=0.3$ でも $score\approx0.21$ となり下限 0.05 を大きく超えるため、候補集合の欠落で説明が付く）。
- **自分の答えだけ記録が遅れていた**：反復が作る MI は `materialize_now=True` を await して埋め込みまで済むが、本応答だけ背景の永続化（実測2秒）に委ねられ、次の反復が「さっき何と言ったか」を拾えなかった。発話の時点で O に書き、**求めを閉じる側**にする（子として書くと `superseded_by` が入り候補から外れる）。
- **STT が「聞き取れない」と言ったものを LLM へ渡していた**：`（聞き取り不能）` の印は、括弧を外して何も残らないときしか落とされず、後ろに文が続くと通り抜けた。周囲の会話が書き起こされてターンを起こし、聞き返し→その声をまた拾う→また聞き返す、で35秒に7回喋った。印を**含む**なら落とす（ループを起こす前に捨てる）。ElevenLabs は `logprob` を返せるが**タイムスタンプ付きの変種でだけ**で、閾値と束ね方を実測なしに決められないため未着手。
- **GUI に何も表示されなかった**：GUI は「発話は `on_action("say")` で来る」前提で、素テキストは say の前の途中経過としてしか扱わない。イベント駆動ループは `on_text` にしか流していなかった（CUI では見えていた）。
- **静穏時間が人への返事まで止めていた**：起点を区別せず掛けており、夜に話しかけると返事が `pending_speech` へ溜まって翌朝に届く動きになっていた。

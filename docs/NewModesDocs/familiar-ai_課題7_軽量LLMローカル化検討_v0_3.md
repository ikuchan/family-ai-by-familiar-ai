# familiar-ai 課題7 再検討 軽量LLM のローカル化検討（レイテンシ優先の選定）（v0.3）

## 位置づけ

本書は選定のための調査設計であり、モデルの採否を決める文書ではない。軽量LLM の担当と同期経路は「I内部設計根拠 v0.2」と「設計図 Mermaid v0.32」に、資源の実測前提は「計測台帳 v0.5」に依る。用語は用語一覧「I 内部再設計」節を参照し、本書で新規に使う語は末尾「用語追記」にまとめる（用語一覧への追記が要る）。

## 1. 現状（事実）

軽量LLM の実体と担当。【事実】設計図 Mermaid v0.32 と用語一覧 v0.21 より、補助LLM＝軽量LLM は Gemini flash-lite で、評価器（APR）と調停器（ARB）が LLM担当（LLH）経由の内部資源として使う。主LLM（生成器のフルLLM）は sonnet。

軽量LLM が担う処理。【事実】I内部設計根拠 v0.2 より、担当は五つある。評価器が機械驚き A≥0.25 のとき W と M と D と A を見て P/Pn/Dom を直接出力し、感情と値踏みと意味づけと要約を行う。調停器が候補から一つ選ぶ（構造化・非対話）。会話の重さを自己判断して三分岐へ振り分ける。短文で閉じる会話に応答し、フル本応答の前に相槌などのつなぎを即答する。用例⑥で発話から想起の重みプロファイルを出す。出力の大半は構造化（数値、候補選択、プロファイル）で、自然文は短文応答とつなぎに限られる。

レイテンシがループの前景遅延に直結する理由。【事実】I内部設計根拠 v0.2 と設計図 Mermaid v0.32 より、評価器の appraisal は案A（同期）でループ内に入り、調停も各反復で候補を選ぶ同期処理である。つなぎ即答は、続けて同期で起こすフル本応答の体感レイテンシを埋めるための前置きである。したがって、これらの同期経路にある軽量LLM の応答遅延は、そのまま前景の反応の遅さになる。これが本課題でレイテンシを第一基準に置く理由である。

自己認識 MI への依存。【事実】設計図 Mermaid v0.32（課題6-1）より、自己認識 MI（システムプロンプト）は評価器とフルLLM 双方のシステムプロンプトで、評価器にとって最重要である。モデルを替えるとき、Gemini 向けに書いたこのプロンプトが別モデルで同じ意図で効くとは限らない。

## 2. 選定の目的と基準

第一基準はレイテンシである。品質を Gemini flash-lite と同等以上に保った上で、同期経路（評価、調停、つなぎ）の遅延が Gemini 以下に収まることを最優先で確かめる。コスト削減は付随の便益として測るが、レイテンシを犠牲にしてまで優先しない。レート律速の解消は副次で、ローカル化で外部 RPM 制約が消える一方、GPU の同時実行が新たな制約になるため、効果と制約を対で見る。

## 3. 候補帯（RTX 3060 12GB 前提）

【事実】Qwen 公式ほか（2026-07 時点）より、Qwen3 の密モデルは 0.6B から 32B（0.6B、1.7B、4B、8B、14B、32B）で、GGUF や AWQ の量子化版があり Apache 2.0 ライセンスである。Q4（4bit 量子化）で Qwen3-4B は約2.5GB、Qwen3-8B は 5〜6GB VRAM、14B は約10GB を要する。ツール呼び出しと JSON 出力は全サイズが対応し、OpenAI 互換 API 形式で、思考モードと非思考モードをプロンプトで切替できる。より新しい世代として、Qwen3.5 の小型モデル（9B、4B、2B、0.8B）が2026年3月に公開されている。

VRAM 予算の見立て（要実測）。計測台帳 v0.5 の同時常駐ピークは 1,838 MiB（知覚と音声と埋め込み）で、推奨構成でも最大約4.2GB、実用空きは 12,188 MiB である。ここから軽量LLM に割ける VRAM は概ね 8GB 前後と見込むが、これは計測値ではなく、同居の実測で確定する。この予算では Q4 の 4B（約2.5GB）と 8B（5〜6GB）が同居候補で、14B（約10GB）は同居では外れる。レイテンシ優先の観点では遅延の小さい 4B や小型の 3.5 世代が有力になりうるが、品質が同期経路の役割に足りるかは実測で切り分ける。

思考モードの扱い（事実）。構造化と調停とつなぎはレイテンシが要件なので、思考モード（連鎖推論を挟みトークンと遅延が増える）は使わず、非思考モードを前提にする。評価軸のレイテンシは非思考モードで測る。

## 4. 検討項目（状態付き）

他課題と同じく、各項目に状態を付けて進める。

〔確定〕合否ライン。品質は、役割ごとに人手で作る正解に対する一致率と差分で測り、候補が Gemini flash-lite を下回らないことを条件にする（Gemini の出力をゴールドにはしない）。レイテンシは、同期経路の初回トークン遅延と総生成時間が Gemini flash-lite 以下であることを合格条件にする。

〔未着手〕評価セットの作成と人手正解づけ。上の合否ラインに必要な、役割ごとの入力例と人手正解を用意する作業。これ自体を一つの管理項目として扱う。対象は評価器の P/Pn/Dom、調停の候補選択、重さ三分岐、重みプロファイル、短文応答とつなぎである。役割ごとに、入力例の出所（用例①A、①B、⑤、③ の W を素材にする）と正解づけの担当を決めてから着手する。人手正解が揃わない役割は、その役割の実測を保留する。

〔未計測〕レイテンシ（第一基準）。非思考モードで、評価器の P/Pn/Dom 出力、調停の候補選択、つなぎ即答、短文応答のそれぞれについて、初回トークン遅延と総生成時間を測る。知覚と音声が同時に動く負荷下での劣化も測る（アイドル単体だけで判断しない）。候補は Q4 の 4B と 8B。

〔未計測〕VRAM 同時常駐。知覚と音声と埋め込みに候補LLM を加えた同時ピークを実機で測る。OOM しない側だけでなく、会話中に評価と調停が候補LLM を叩くピークで破綻しないかを確かめる。Q4 の 4B と 8B、および既存スタックを推奨構成（最大約4.2GB）へ振ったときの合計を測る。

〔未計測〕構造化出力の妥当性。P/Pn/Dom の対 Gemini 差の分布と範囲逸脱率、候補選択の一致率と誤選択率、重みプロファイルのスキーマ順守率を測る。両側で見る。正しく出る入力だけでなく、崩れをパース失敗として検出できるか、選ぶべきでない候補を実際に外せるかを対にする。入力は上の評価セットを用いる。

〔未計測〕プロンプト移植性。Gemini 向けの自己認識 MI（システムプロンプト）が候補モデルで同じ意図で効くかを確かめる。効かない場合、モデル差かプロンプト差かを切り分ける。

〔未計測〕コスト（付随）と律速（副次）。想定リクエスト量あたりの API 従量と、ローカルの電力と GPU 占有を比較する。ローカル化で Gemini Free の 15 RPM と MaxConc の外部律速が消える一方、GPU の同時実行が新たな上限になることを、トークン毎秒と占有から見る。

〔要決定〕置換か併存か。上の結果を見て、Gemini を完全に置き換えるか、ローカルを主として Gemini をフォールバックに残すかを決める。これは設計方針の段で原因と対応案として出す。

## 5. 未決事項（設計方針の前に決める）

合否ラインの基準づけは人手正解で確定した。残る未決は、評価セットの用例選定（上の管理項目で詰める）と、候補モデルの世代（Qwen3 か Qwen3.5 小型か）である。これらが決まってから実測を回し、結果を持って設計方針へ進む。

## 用語追記（用語一覧へ反映が要る）

- **ローカルLLM**：自機の GPU 上で動かす公開重み LLM。外部 API を介さない。
- **Qwen**：アリババの公開重み LLM 系列（固有名詞）。
- **推論ランタイム**：ローカル LLM を実行する基盤（Ollama、vLLM 等）。
- **量子化**：モデル重みを低ビット表現へ圧縮し、VRAM と計算量を減らす手法（既存の int8 の一般化）。Q4 は 4bit 量子化。
- **量子化フォーマット**：GGUF、AWQ 等の重み格納形式。
- **トークン毎秒**：1秒あたりの生成トークン数（生成スループット）。
- **初回トークン遅延**：プロンプト投入から最初のトークン出力までの時間。
- **思考モードと非思考モード**：Qwen3 の切替可能な生成モード。思考モードは連鎖推論を挟み遅延が増え、非思考モードは即答寄り。

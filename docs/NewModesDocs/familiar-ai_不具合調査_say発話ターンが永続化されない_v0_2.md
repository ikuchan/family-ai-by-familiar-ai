# familiar-ai 不具合調査：say() で話したターンが永続化されない（v0.2）

> v0.2：`say()` の役割を実物で確かめ、設計方針を組み直した。当初案（本文と発話のどちらか一方を選ぶ）は採らない。**そのターンに自分がしたこと**として、考えたこと（本文）と話したこと（`say()`）を区別せず記録する。あわせて周辺の不整合を2件記録した。auto-say はコードの既定がオンなのに `.env.example` は「既定オフ」と書いており食い違う。`gui.py` のコメントは複数の `say()` が全部表示されると書いているが、実装は2回目以降を抑制する。**auto-say は機構ごと撤去**と決めた。記録の粒度（1周ごと）は新ループ（[D-反復出力]）とセットでないと意味を成さないため、この修正では変えない。作業の順序も決めた。

> v0.1：スライス3（e 軸のスコア接続）の実機確認中に、会話しても記憶が一切書かれないことに気づいて調べた。真因は `agent.py` の永続化判定が本文テキストだけを見ていることで、`say()` だけで話したターンは「返事が無かった」と扱われ、観測・会話 summary・mood・メンタル状態のすべてが書かれない。設計方針まで承認済み。実装は未着手。

## 切り分けの経過

永続化はすべて非同期・遅延型で、既存ログからは「試みていない」のか「試みて途中で終わった」のかを判別できなかった。そこで通過点を計測するログを一時的に仕込み、実機で採取した。

途中で立てた仮説と、その反証も記録しておく。

- **仮説：終了時に背景タスクが打ち切られている。**最初のターンから終了まで2分あり、全ターンの欠落を説明できないので棄却した。
- **仮説：ループ上限に当たって永続化まで届いていない。**`_BRIEF_REPLY_MAX_ITERATIONS=2` と `say` 催促の `continue` が噛み合う筋を疑ったが、「Reached max iterations」の警告が出ていないので棄却した。
- **仮説：`final_text` が `"(no response)"` になっている。**画面に返事が文章で表示されている以上 `result.text` は空でないはずで、いったんは不利と判断した。しかし計測すると、表示されていたのは `say()` に渡された文字列であり、モデルの本文出力ではなかった。これが真因である。

## 真因

計測ログの実物。

```text
[書込調査] iter1 stop_reason=tool_use text='' tools=['say']
[書込調査] iter2 stop_reason=end_turn text='' tools=[]
[書込調査] end_turn 分岐の末尾 final_text='(no response)'
```

エージェントは本文テキストを書かず、`say()` ツールだけで話す。よって `result.text` は空になり、`final_text` は `"(no response)"` になる。`agent.py` の永続化判定

```python
if final_text and final_text != "(no response)":
```

が偽になり、この条件の下にある永続化がまとめて飛ばされる。

飛ばされるのは次の3つで、確認した欠落と一対一で対応する。

| 飛ばされる処理 | 欠落 |
|---|---|
| `mental_state_bus.append` | `mental_state_log` が空 |
| `_run_post_response_pipeline` の spawn | 観測・会話 summary が書かれない |
| パイプライン内の `nudge_current_mood` | `agent_state` に `mood_pad` の行が無い |

## 影響範囲

会話が `say()` だけで完結するターンでは、記憶も気分も残らない。最後の書き込みが 2026-06-29 であることと整合し、**スライス3（e 軸）より前から壊れていた**。想起側の改造とは独立である。

この不具合が直るまで、想起の実機確認は成り立たない。mood が中立から動かないので、気分一致想起（シナリオ1）が原理的に観測できないためである。

## `say()` の役割

ツール定義（`tools/tts.py:233-236`）は「Speak text aloud. Use this to communicate with people in the room.」であり、`say()` は**人に届く発話**そのものである。TTS が読み上げ、GUI が発言として表示する。沈黙制御（在室・静穏時間）のゲートもここに掛かる。

本文テキスト（`result.text`）は扱いが違う。`say()` が発火すると GUI は `self._stream.discard()` で、それまで流していた本文を捨てる（`gui.py:1926`）。本文は下書き・内心に近い位置づけである。

## 設計方針〔承認済み〕

ターンで起きたことの実体が本文テキストと `say()` の引数の2通りあるのに、永続化の判定が本文テキストだけを見ているのが原因である。

**そのターンに自分がしたこととして、考えたことと話したことを区別せず記録する。**どちらか一方を選ぶ当初案は採らない。内心を「考えたが言わなかったこと」として残すのは記憶として自然であり、片方を捨てる理由がないためである。

- ターン中に `say()` が呼ばれたら、実際に届いた発話を保持する。2回目以降の `say()` は音声も画面表示も抑制される（`agent.py:3908`・`on_action` も重複時は呼ばれない）ので、届いた最初の1回だけを使う。
- 永続化の判定と内容は、本文と発話を合わせたものを対象にする。どちらか片方しか無ければ、あるほうを使う。
- 両方とも無いターン（沈黙を選んだターン）は、従来どおり何も書かない。

別案の「本文が空でも常に永続化する」は採らない。沈黙のターンまで記録され、`"(no response)"` が観測として残るためである。

## 周辺で見つかった不整合

修正の対象そのものではないが、同じ機構の周りで実装と記述が食い違っている。

- **auto-say の既定**：`config.py:306-310` は環境変数が未設定なら `True` を返す（`("0","false","no")` に含まれないため）。一方 `.env.example:185-191` は「Autonomous behavior (default: all OFF)」「By default, the agent only responds when spoken to and uses say() explicitly」と書く。実機は `.env` に記載が無く、auto-say がオンで動いていた。
- **重複 `say()` の扱い**：`gui.py:1922-1923` のコメントは複数の `say()` が順に全部表示されると書くが、`agent.py:3908` は2回目以降の音声を抑制し、`on_action` も呼ばない。コメントが実装とずれている。
- **設計の正本が無い**：沈黙制御と `say()` の位置づけを書いた設計ドキュメントが `docs/NewModesDocs/` に無い（CHANGELOG に記述があるのみ）。

## auto-say の撤去〔承認済み〕

auto-say は機構ごと撤去する。話すかどうかをモデルの判断（`say()` を呼ぶか）に委ねるために発話をツールへ切り出したのに、呼ばなかったターンで機械が本文を代弁するのでは、切り出した意味が消える。ゲートは在室と静穏時間だけで内容の検討を挟まないため、下書きのつもりの本文がそのまま読み上げられうる。新ループでも要らない機構である。

## 記録の粒度と新ループの関係

「ループが一つ回るたびに、自分のやったこととして記憶する」という粒度は、新ループの1周（**1反復＝1出力**・[D-反復出力]）に対応する。新ループでは、いまの「ターンの中でイテレーションを何周も回す」入れ子が撤去される（`設計図_Mermaid` [D-周期]／`gap分析_移行設計` の tape 廃止）。

現行コードにその1周は存在せず、ターンとイテレーションの2階層がある。どちらの階層に記録を付けても新ループとずれるので、**この修正では粒度を変えない**（ターン単位のまま）。1周ごとの記録は新ループへの移行で実現する。

## 作業の順序〔承認済み〕

3つを別の作業として分け、次の順で進める。

1. **止血**＝本不具合の修正。粒度は変えない。実装は TDD で、RED は「`say()` だけで話したターンで永続化が走る」を落とす形にする。あわせて一時的な計測ログ（`[書込調査]` で始まる行）を外し、実機で観測・会話 summary・`mood_pad` が書かれることを見る。
2. **auto-say の撤去**。挙動変化。
3. **新ループ（[D-反復出力]）への移行設計**。`agent.py` の `run()` の分解を、整理ではなく移行の地ならしとして設計ドキュメントに起こす。

止血を先にするのは、壊れていることが分かっている 795 行の関数を、そのまま組み替えるのが危ないためである。止血を現行の粒度にとどめるのは、後で捨てる作業を最小にするためである。

止血が済んだら、スライス3 の実機確認（`実機確認シナリオ_想起` のシナリオ1〜3）をやり直す。mood が動かない限り気分一致想起は観測できないので、順序は逆にできない。

## 2. いまのパジュで分かっていること（2026-11-24・コードを読んだ事実）

| 事実 | 根拠 |
|---|---|

アプリのボタンは、いまの `/speaker 〈名前〉` と同じ働き（話者をはっきり指定する）にできる見込みが高い〔推測〕。

## 6. 端-b の設計方針（機体の外の口・2026-11-25 から本人と決めている）

### 6.1 いまの入口と出口（コードを読んだ事実）

| 事実 | 根拠 |
|---|---|
| 人の言葉は、声も打った言葉も、同じ入口（`push_utterance`）から 1 つの待ち行列に並ぶ。求めは同時に 1 つで、順に答える | `loop/event_loop.push_utterance`、`_take_trigger` |
| 打った言葉（入口の種類 `keyboard`）は、名前を呼ばれた言葉と同じに扱う（名前の窓を見ない） | `event_loop`（`named=… or source == "keyboard"`） |
| 返事は、家のスピーカーで声にし（`_say_aloud`）、画面へも出す（`_emit`）。打った言葉への返事も、家で声になる | `event_loop._speak`、`_emit` |
| 考えているあいだは、家のスピーカーで待ちの電子音と合図を鳴らす | `event_loop._beep_while_waiting`、`io/dif.play_cue` |
| 外の口を作る部品（待ち受けの `aiohttp.web`）は、いまの依存の `aiohttp` に入っている。依存は増えない | `pyproject.toml` |

### 6.2 原因と対応案

アプリから届いた言葉は、いまの入口にそのまま流すと、返事が家のスピーカーで声になり、電子音も家で鳴る。いまの作りには「この求めの返事をどこへ返すか」が無く、返事の出口がいつも家だからである。

対応案は、求めに**返事の行き先**（家か、どの端末か）を持たせ、アプリから届いた言葉の求めでは、返事の字を話しかけた端末へ返し、家の声と電子音を出さないことである。入口は、いまの打った言葉と同じ道（名前を呼ばれた言葉・話者を明示した言葉）を通す。

|---|---|

| b2 | アプリから、家で音が出る頼み（音楽、タイマー、アラーム）を受けるか |
| b3 | アプリで話した人を、家のそばに居る人として数えるか |
| b4 | 家で「黙って」と頼まれているあいだも、アプリには返事をするか |
| b5 | パジュから話しかける言葉（自発）を、アプリへ送るか |

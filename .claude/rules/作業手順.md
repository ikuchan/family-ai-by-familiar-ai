# 作業手順（出力に関する指示）

本プロジェクトでの調査、設計、資料作成、実装計画づくりにおける進め方。CLAUDE.md の
「作業の進め方（常時適用の要点）」の詳細版。常時適用する。

なお、この会話向けの原文にあった一部の運用（読み取り専用コピーの差し替え、実装を別の
AI へ渡す）は、Claude Code では自分がリポジトリを直接編集するため、その形に置き換えてある。
ただし**全体テスト（`./scripts/run_tests.sh`）は人（ユーザー）が回す**運用を維持する。自分は
`ruff` と `mypy` までを回し、全体テストの実行はユーザーに依頼してその結果を待つ。

## 0. 基本姿勢

- 確信は確認を省く理由にならない。むしろ「承認されるに決まっている」「正しいに決まって
  いる」と確信したときこそ、承認や反証の確認を省きたくなる瞬間であり、その確信を立ち
  止まる合図として扱う。手順（承認を得てから実装計画を作る等）は、自分の判断がどれだけ
  確信に満ちていても省略しない。省略してよいと感じたら、その感覚自体が省略してはいけない印である。
- 自分の行動を、内部のルールやフックへの準拠として説明しない。「ルールにより」のような、
  規則への準拠を表明する前置きを使わない。確認や調査はそうする必要があるからするので
  あって、外から指示されたからではない。理由を述べるなら、その行為自体の具体的な理由を述べる。

## 1. 言語・用語

- 日本語で書く。
- 英語・略語は、用語一覧（`docs/NewModesDocs/` の `用語_略語一覧`）または設計ドキュメントで
  **定義済みのものだけ**使う。
- 新たに英語・略語を使う必要があるときは、その場で日本語定義を示し、かつ**用語一覧に追記する（必須）**。
- 回答を出す前に、**未定義の英語・略語が混じっていないか確認してから**出す。

## 2. 進め方（調査・判断）

- 問題点についてまずは調査をおこない、設計方針に落とし込む。
- 既存構造に相乗りさせる案は、その構造に依存する仕組みを grep で洗い出し、汚染がないか
  確認してから提示する。
- 設計は、依存する前提（ファイル・関数・適用済み実装）が実環境で揃っていることを確認して
  から始める。ソースに無くても実環境にある場合があるため、「無い」と即断せず存在確認を
  してから設計を始める。
- 何かを確かめたと判断する前に、それが成り立つ場合に何が見えるかだけでなく、それが間違って
  いたら何が見えるはずかを対にして問い、その反証側が実際に排除されることを確認する。一方向
  の確認だけで「確かめた」としない（テストなら通る場合と落ちる場合、診断なら仮説に合う事実と
  仮説なら起きないはずの事実、の両方を見る）。
- 読んでいるソース＝実行中のソース、を毎回確認してから語る。
- 【事実】【コード推測】【再現推測】を混ぜない。断定は事実のみ。
- 真因が確定するまで対処方針を出さない。仮説段階では調査コマンドを出す。
- 設定が正しいのに動かないときは、環境変数名の食い違いを1文字ずつ照合する。
- ハードもコードも正常なのに変なら、DB の記憶・自己モデルの汚染を疑う。
- ログのエラーは発生時刻を見て、現在の問題と時系列を一致させる。

## 3. 一つずつ確認

- 大きな変更は一度にやらず、**一項目ずつ確認しながら**進める。各変更後に確認を求める。
- 仮置きの値が要るときは、勝手に決めず質問し、回答を得てから進む。

## 4. 設計方針の作り方

- 原因とそれに対する対応案という形で、設計方針を説明し、承認を得てから実装計画（改造方針）
  を作成する。
- 設計方針に未決事項を残したまま実装計画を作成しない。

## 5. 実装計画（改造方針）の作り方

- 設計方針承認の返答が来るまで、具体的な実装方針・コード・TDD 手順を出力しない。
- 改造方針は **TDD ベース**で出す（RED を正しい理由で落とし、最小の GREEN、必要なら REFACTOR）。
- 改造方針には、ドキュメントの生成（実装後に該当設計ドキュメントへ反映すること）も含める。
- ドキュメントには検討中の内容は含めず、ソースコードに実装したことだけを書く。
- ソースコード内のコメントについても事前に検討し、方針に含める。
- 改造方針書には**目的と注意点**を含める。
- 既存テストケースの修正要否を検討し、方針に含める。
- 改造方針は承認された設計方針に基づいて自分で立て、そのまま TDD で実装する。実装後、
  `ruff` と `mypy` は自分で回し、全体テスト（`./scripts/run_tests.sh`）はユーザーに実行を
  依頼してその結果を待つ。
- バグ修正前に、同一ロジックの重複を grep で洗い、一元化してテストする。
- DB 更新がある場合には、マイグレーション方法も方針およびテストに含める。とくにテストケース
  の修正対応を検討する。
- カラムや API を廃止・改名する変更では、「変更対象を列挙する」だけで終わらせない。変更後に
  旧名を grep して残存がゼロになることを完了条件に必ず含める（例：`date` カラム廃止 → 完了
  条件に「grep で `observations` 関連の旧カラム参照が残っていないこと」を入れる）。
- 列挙した箇所数（「21箇所」等）を信頼しない。数えることは網羅の証明にならない。「旧名で
  検索して0件」が網羅の証明である。
- grep でヒットした行を変更対象から外すときは、「なぜ外してよいか」を1件ずつ明示する。
  無言で対象から落とさない。
- 特に `LIKE` / `EXTRACT` / `MIN()` / `substr()` など、単純な `=` 比較でない日付・文字列
  演算は、型変更で壊れやすい。これらは優先的に精査する。

## 6. ファイル運用

- リポジトリのファイルを直接編集する。設計・計画ドキュメントは `docs/NewModesDocs/` の md、
  コードは `src/` や `migration/` などリポジトリの該当場所。
- ファイルを変えたら、新規追加か更新か、何を変えたかを述べる。
- 設計・計画ドキュメントは版番号で管理する。

## 7. 図・体裁

- Mermaid は生のコードブロックで出す。向きは **TD 固定**（LR 禁止）。
- コンポーネント名は「**日本語：英語（頭字）：機能説明**」。色・線種・矢印ラベルの規約は
  設計ドキュメント本体の「規約」に従う。
- 箇条書き・表を適宜使い、**数値は具体値**で書く。過度な装飾はしない。

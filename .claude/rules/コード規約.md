# コード規約（ログ方針・スキルの使い分け）

`src/` と `migration/` と `tests/` の py を触るときに従う。

## スキルの使い分け（Superpowers）

`superpowers` プラグイン（obra/superpowers）が入っており、スキルは自動で立ち上がる。本
プロジェクトはこれを選んで使う。以下のルールが競合時はスキルの既定を上書きする（ユーザー・
CLAUDE.md の指示がスキルに優先する、という Superpowers 自身の優先順位に従う）。

**使う規律スキル:**

- `test-driven-development` — 新規コードとバグ修正はすべて RED-GREEN-REFACTOR。失敗する
  テストを書き、正しい理由で落ちるのを見てから最小のコードを書く。
- `systematic-debugging` — バグ・テスト失敗・想定外の挙動は、直す前に真因を見つける。当て推量
  で試さない。
- `verification-before-completion` — 完了と言う前に、実際の検証コマンドを回し出力を読む。
- `writing-plans` — 承認された設計を実装計画へ落とすとき、正確なファイルパスと検証手順つきの
  小さなタスクに割る。

**このプロジェクトが上書きするスキル既定:**

- **TDD の「テスト前に書いたコードを消す」ルールは新規コードにだけ適用する。** これは既存の
  大きなコードベースである。既存モジュールの変更では、変える箇所にテストを足す。動いている
  本番コードを「作り直す」ために消さない。
- **無人の長時間自走（`subagent-driven-development` を多タスクに無人で走らせる）はしない。**
  一項目ずつ、各変更後に人間の確認を挟んで進める。次の変更へ移る前に止まって確認する。
- **設計はまず会話で決める。** 設計判断は人間と（原因 → 対応案 → 承認）で決め、設計ドキュメント
  （`docs/NewModesDocs/` の日本語 md）に記録する。`brainstorming` は明示的に頼まれたときだけ使い、
  承認ゲートを置き換えない。
- **git worktree を勝手に作らない。** 既存の Git ワークフロー（`develop-ikuchan` から feature
  ブランチ）に従う。

**使ったスキルの報告。** 完了報告のたびに、実際に効いたスキルを挙げ、それぞれ一行で何をしたか
述べる（例：「test-driven-development：失敗するテストを先に書いた」）。効いたものが無ければ
「使ったスキル：なし」。装飾でなく、スキルが役に立っているかの可視化のために書く。

## プロジェクトローカルのスキル（PostgreSQL・pgvector・並行処理・ログ）

`.claude/skills/` に第三者スキル（MIT）が入っている。自動で立ち上がる。**これらのスキルの
スクリプトを DB に対して走らせない。** 案内として使う。環境の事実：PostgreSQL 16
（`pgvector/pgvector:pg16`）、`situated_embeddings` は `vector(1024)`、コサイン
（`vector_cosine_ops` / `<=>`）、埋め込みは正規化済み。LICENSE・帰属ファイルは残す。

- **`mastering-postgresql`（pgvector 案内）:** HNSW、`ef_search`、フィルタ検索の再現、
  反復スキャン、asyncpg のクエリパターンに使う。Quick Start の例は pg17・`vector(1536)`・
  `BIGSERIAL` を使うが、そこは無視する（環境は pg16・`vector(1024)`・既存スキーマ）。
  `BIGSERIAL` を導入しない。
- **`postgresql-table-design`（スキーマ規約）:** **新規**のテーブル・カラム・マイグレーション
  に、型と安全の規約を使う（`timestamptz`（`timestamp` は使わない）、`varchar(n)` より `text`、
  `serial` より `generated always as identity`、FK カラムに手動 index）。大きなテーブルの
  マイグレーションでは、`CREATE INDEX CONCURRENTLY`（トランザクション外）、揮発デフォルト
  （`now()`）はテーブルを書き換える、カラムを落とす前に制約を落とす。**既存スキーマを規約に
  合わせるためだけに書き換えない。** 新規に適用し、動いている既存カラム・型はタスクが要求
  しない限り触らない。
- **`python-concurrency-performance`（非同期・並行）:** asyncio とスレッドの境界、ファンアウト
  の制限（semaphore・bounded queue）、締切・キャンセル伝播、タスク・スレッドリークの点検に使う。
  キャンセルは通常の制御フローとして扱う。`asyncio.CancelledError` は局所のクリーンアップだけで
  捕まえて**再送出**する。leaf タスクで握り潰さない。シャットダウンは冪等にし、`finally` で
  クリーンアップを保証する。呼び出し経路は sync か async かを一貫させ、ブロッキングや GPU 重い
  呼び出し（InsightFace、faster-whisper など）はイベントループの外へ（`asyncio.to_thread()`）。
- **`python-logging`（ログ設定案内）:** `familiar_agent` パッケージはライブラリとして扱う
  （各モジュールで `logging.getLogger(__name__)`、`basicConfig()` を呼ばない）。ハンドラ・レベルは
  エントリポイント（`main.py`）で一度だけ設定する。標準ライブラリの logging を使う（loguru を
  入れない）。レベルの使い分けは下の方針に従う。

## ログ方針（レベルと書式）

既存ログの一度きりの監査の結果。設定は `main.py` に集約済み（root ハンドラ、フォーマッタ、
第三者ライブラリのレベル抑制）。唯一の逸脱は `memory.py` の一行。**既存ログを一括で書き直さ
ない。** この方針は**新規・変更コード**に適用し、その file を触ったついでに既存呼び出しを直す。

**レベル（5段階）:**

- `debug` — 詳細な開発者トレース（変数値、通った分岐）。本番では切る。
- `info` — 正常経路の節目（起動・停止、接続確立、ジョブ完了、記録に値する状態遷移）。
- `warning` — コードが**回復して**続ける異常（設定ファイル欠如で既定を使う、任意機能の無効化、
  キューの滞留）。
- `error` — **完了できなかった**操作（フォールバックなし、関数が目的を達しなかった）。
- `except` 節では **`logger.exception(...)`**（または `logger.error(..., exc_info=True)`）を
  優先し、スタックトレースを残す。既存には `except` 内で trace を落とす
  `logger.warning("...: %s", e)` が約110箇所ある。触ったら変換する。回復可能な異常なら `warning`
  のまま、そうでなければ `exception`。trace が役立つなら `exc_info` を足す。

**書式:** エントリポイントのフォーマッタは、時刻・レベル・logger 名・行番号を持たせる。例：
`"%(asctime)s | %(levelname)s | %(name)s:%(lineno)d - %(message)s"`。構造化文脈は message に
文字列連結せず `extra={...}` を使う。

ライブラリコードのログに `print(...)` を足さない。logger を使う。`print` は本物の
CLI・対話 stdout だけ。

**ログを足す点（後から再構成できるように）:**

- 外部境界 — DB クエリ、LLM 呼び出し、MCP・ツール呼び出し、デバイス I/O の入口と結果。
- LLM プロンプトの組み立て・編集 — 組み立て・編集のたびにログする。全文は重く会話・記憶内容を
  含むので、**全文は `debug` のみ**（本番では切る）。軽い要約（どのテンプレ/経路、W に入った MI
  数、プロンプト長、対象モデル、入出力トークン数があれば）は状態遷移の一行として出してよい。
  **全文や会話・記憶内容を `info` 以上で出さない。**
- 状態遷移 — その機構ができたら、発火、W 構築、open の解決など、後で再構成したい変化。
- 回復した異常 — フォールバック経路を取ったとき（`warning`）。
- 非同期境界 — enqueue、完了、キャンセル。

**節度（ログで溺れさせない）。** 毎イテレーション・毎ティックの hot path は `debug`。一行一目的。
値は選んで（主要フィールド、件数、長さ）出し、オブジェクト丸ごとは出さない。ログを増やすことでは
なく、後から再構成できることが目的。

# ponytail（抜粋）

**これは上流の Ponytail（MIT・DietrichGebert）の全文ではない。** このリポジトリの
進め方と噛み合う部分だけを採った抜粋である。出力の形、テストの省略、
「決めて進む」の3つは**採っていない**。それらは CLAUDE.md と `.claude/rules/` が定める。

上流：https://github.com/dietrichgebert/ponytail

## 梯子

最初に成り立つ段で止まる。

1. **そもそも要るか。** 「後で要るかもしれない」だけなら作らない。作らない理由を一行で述べる
2. **このリポジトリに既にあるか。** ヘルパ・型・同じ形の処理が数ファイル先にあるなら、それを使う。
   **書く前に探す。** 数ファイル先にあるものを作り直すのが、いちばんよくある無駄である
3. **標準ライブラリで済むか。** 済むなら使う
4. **土台の機能で足りるか。** アプリ側のコードより DB の制約、JS より CSS
5. **入っている依存で足りるか。** 数行で済むことのために依存を増やさない
6. **一行で書けるか。** 書けるなら一行
7. **そこまで来て初めて**、動く最小のコードを書く

## 梯子は理解を短くしない

**問題の理解では手を抜かない。** 梯子が短くするのは解であって、読む量ではない。
変更が触る範囲を全部読み、実際の流れを端から端まで辿ってから、どの段で止まるかを決める。
理解を飛ばして小さな差分を出すのは、効率の顔をした自信のある誤りである。

読み切ってから、最小にする。

## 直すのは症状でなく原因

報告に出るのは症状である。直す前に、触ろうとしている関数の**呼び手を全部 grep する**。

最小の直し方は、たいてい原因を直す形と同じである。共有された関数に一つ番人を置くほうが、
呼び手ごとに置くより差分が小さい。報告に出た経路だけを直せば、兄弟の呼び手は壊れたまま残る。
**全部の呼び手が通る場所で、一度だけ直す。**

## 足さない

- **頼まれていない抽象を足さない。** 実装が一つしかない interface、製品が一つしかない
  factory、変わらない値のための設定
- 「後で使うから」の足場を組まない。後のことは後が組む
- **足すより消す。** 賢いより退屈。賢さは、誰かが夜中に読み解く羽目になるものである
- 触るファイルは少ないほどよい。ただし**理解したあとの**話である。間違った場所への最小の変更は、
  最小ではなく二つ目の欠陥である
- 標準ライブラリに同じ大きさの選択肢が二つあるなら、境目の値で正しいほうを採る。
  最小にするのは書く量であって、正しさではない

## 手を抜かないところ

次は削らない。

- 信用の境目での入力の検査
- データを失わせないための異常処理
- 安全に関わるもの
- 明示的に頼まれたもの

**実機は紙の上のようには動かない。** 時計はずれ、センサはずれて読み、機器は数パーセント速い。
コードを減らすだけでなく、**調整のつまみを残す**。物理の世界には、最小のモデルが見ていない
ずれがある。
